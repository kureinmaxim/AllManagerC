# Version Management — AllManagerC

Единый порядок управления версиями приложения, установщиков и документации.

Источник версии — `config.json`, поле `app_info.version`. Команды работают на
Python 3.10+ без установки дополнительных библиотек. Само приложение проверяется
на Python 3.13.

## Быстрые команды

Выполняйте из корня проекта `AiManage-Clean` или клонированного `AllManagerC`.
Скрипт определяет корень по собственному расположению, поэтому его также можно
запустить по абсолютному пути из другой папки.

### macOS / Linux

```bash
python3 scripts/version.py status
python3 scripts/version.py check
python3 scripts/version.py sync
python3 scripts/version.py bump patch
python3 scripts/version.py bump minor
python3 scripts/version.py bump major
python3 scripts/version.py set 6.0.2
```

### Windows

```powershell
python scripts\version.py status
python scripts\version.py check
python scripts\version.py sync
python scripts\version.py bump patch
python scripts\version.py bump minor
python scripts\version.py bump major
python scripts\version.py set 6.0.2
```

Это отдельные примеры команд, а не последовательность для запуска целиком.

## Источник версии

```json
{
  "app_info": {
    "version": "6.0.2"
  }
}
```

Формат — `MAJOR.MINOR.PATCH`: три неотрицательных целых числа без ведущих нулей.
Префикс `v` используется только в Git-теге. Предварительные версии вроде
`6.1.0-rc1` сейчас не поддерживаются.

- `patch`: исправления; `6.0.2` → `6.0.3`.
- `minor`: новые совместимые возможности; `6.0.2` → `6.1.0`.
- `major`: значительные несовместимые изменения; `6.0.2` → `7.0.0`.

## Какие файлы синхронизируются

- `config.json` → `app_info.version`: главный источник.
- `app_version.py` → `VERSION`: версия работающего приложения, попадает в сборку
  через обычный Python-импорт. Не редактируйте этот файл вручную.
- `AllManagerC.iss` → `MyAppVersion`: версия установщика Windows.
- `README.md` и `README_ru.md`: значок версии исходников Shields.

Версия в интерфейсе берётся из `app_version.py`, а не из старого пользовательского
профиля. Обновление профиля сравнивает числовые части версии: `6.10.0` новее `6.9.0`.

Значок **Published release** в английском README показывает последний релиз с
GitHub и может отличаться от версии исходников до публикации. Скрипт его не меняет.
Исторические номера в `CHANGELOG.md` и примерах документации также не заменяются.

## Что делают команды

`status` показывает версии и помечает расхождения. Файлы не меняются.

`check` проверяет то же самое, но возвращает ненулевой код при расхождении,
отсутствующем файле или неправильном формате. Подходит для сборки и CI.

`sync` переносит версию из `config.json` во все зависимые файлы. Вариант
`sync 6.0.2` сначала задаёт указанную версию. Отсутствующие или повреждённые
маркеры требуют исправления: скрипт проверяет все файлы до начала записи.

`bump patch|minor|major` увеличивает нужную часть версии, сбрасывает младшие
части и синхронизирует файлы.

`set 6.0.2` задаёт конкретную версию. Команда допускает понижение версии;
используйте его осознанно и не переиспользуйте уже опубликованный тег.

При изменении главной версии командой `set`, `bump` или `sync X.Y.Z` обновляются
`app_info.release_date` и `app_info.last_updated` на текущую локальную дату.
Обычный `sync` сохраняет даты. Если версия исправлялась вручную в `config.json`,
обновите дату выпуска там же при необходимости.

Остальные настройки в `config.json` сохраняются. Скрипт не открывает базы,
не меняет `.env`, не создаёт Git-коммиты и не публикует релизы.

## Контроль сборок

`tools/build_macos.py` и `build_windows.py` запускают `check` перед сборкой.
При рассогласовании сборка завершается с ошибкой; исправьте файлы через `sync`.

На macOS одна версия используется в конфигурации приложения, полях
`CFBundleShortVersionString` / `CFBundleVersion` и имени DMG. Отдельная стадия
`--stage dmg` сверяет версию готового `.app` с текущей версией проекта:
старое приложение нельзя случайно упаковать под новым номером.

```bash
python3 scripts/version.py check
./build_macos.sh --stage all
```

Новая сборка получает отдельную папку в `dist`. Изменение версии не обновляет
ранее собранные `.app`, DMG или Windows-инсталляторы — их нужно пересобрать.
Подробнее: [BUILD_MACOS.md](BUILD_MACOS.md) и [DEPLOYMENT.md](DEPLOYMENT.md).

## Проверки на GitHub

Workflow `.github/workflows/version-check.yml` на push и pull request:

1. Проверяет совпадение версий.
2. Запускает тесты механизма управления версиями.
3. Для Git-тега дополнительно проверяет его совпадение с `vX.Y.Z`.

Такую проверку можно запустить локально:

```bash
python3 scripts/version.py check --tag v6.0.2
python3 -m unittest discover -s tests -p test_version_management.py -v
```

Workflow не собирает и не публикует установщики автоматически.

## Порядок выпуска

1. Запустите `status` и выберите `bump patch`, `bump minor`, `bump major` или `set`.
2. Опишите изменения в `CHANGELOG.md` и обновите актуальные инструкции при необходимости.
3. Выполните `check` и тесты приложения.
4. Соберите установщики, проверьте запуск и номер версии на нужных платформах.
5. Проверьте Git diff и закоммитьте исходники. Файлы из `dist` остаются вне Git.
6. Отправьте коммит и создайте тег `vX.Y.Z` именно на проверенном коммите.
7. Опубликуйте GitHub Release с установщиками и SHA256. Не заменяйте старый
   опубликованный релиз: для исправления используйте следующий patch-номер.

Версия исходников, тег и версия приложенного установщика должны совпадать.
